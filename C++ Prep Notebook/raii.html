1. Problem: resource lena aasaan, chhodna yaad rakhna mushkil

Resource = koi bhi cheez jo lo toh wapas karni padti hai:

ResourceLenaChhodna
Heap memorynewdelete
Fileopenclose
Mutex locklock()unlock()
Network / DB connectionconnectdisconnect

Purane C style mein sab haath se:

void process() {
    int* data = new int[100];
    if (kuchGadbad) throw runtime_error("error");   // ← yahan se nikal gaye
    delete[] data;                                  // ← ye kabhi nahi chali
}
new int[100] liya
catch: beech mein error  → delete kabhi nahi chala = LEAK

Function se nikalne ke bahut raaste hain: beech mein return, exception, koi if. Har raaste pe delete yaad rakhna practically impossible hai.

2. RAII ka idea

Core idea

Resource ki zindagi ko ek object ki zindagi se baandh do. Constructor mein resource lo, destructor mein chhodo.

class Buffer {
    int* data;
public:
    Buffer(int n) : data(new int[n]) { }   // constructor: LO
    ~Buffer() { delete[] data; }           // destructor: CHHODO
};

void process() {
    Buffer b(100);
    if (kuchGadbad) throw runtime_error("error");
}   // ← b yahan khatam → destructor chalega hi chalega
Buffer: memory LI
~Buffer: memory CHHODI      ← exception aaya phir bhi chhodi
catch: beech mein error

Kaam kyun karta hai? C++ ki guarantee: stack pe bane object ka destructor scope khatam hote hi (} pe) chalta hai, chahe normal return ho, early return ho, ya exception. Delete yaad rakhna ab tumhara kaam nahi, compiler ka hai.

3. Exception mein kaise: stack unwinding

Exception phenka gaya toh C++ function se bahar nikalte waqt har local object ka destructor chalata hai, ulte order mein (jo baad mein bana, wo pehle marega):

void f() { Tag a("A"); Tag b("B"); Tag c("C"); throw ...; }
bana: A   bana: B   bana: C
mara: C   mara: B   mara: A     ← reverse order
catch

Ise stack unwinding kehte hain (interview mein ye shabd zaroor bolna). Reverse kyun? Baad wala object pehle wale pe depend kar sakta hai (pehle file khuli, phir uspe writer bana). Toh pehle writer jaaye, phir file band ho.

5. Traps (simple version)

Pehle ye rule pakka karo

Destructor tab chalta hai jab object ka scope khatam ho, yaani } aate hi. RAII ka saara jaadu isi } pe hai. Trap 1 aur 2 important hain; 3 aur 4 bas ek ek line yaad rakho.

Trap 1: new se banaya toh } ka jaadu nahi chalta

{
    Buffer b;               // stack pe
}                           // } → b khatam → destructor chala ✅

{
    Buffer* p = new Buffer; // heap pe
}                           // } → sirf pointer p khatam hua
                            //      heap wala Buffer abhi bhi zinda ❌
stack:      LI → CHHODI      ✅
heap (new): LI → (kuch nahi) ❌ leak

new se banaya object kisi } se bandha hi nahi. Wo tab tak zinda hai jab tak khud delete na karo. Fix: unique_ptr.

{
    auto u = make_unique<Buffer>();
}   // } → unique_ptr khatam → wo khud delete karta hai ✅
unique_ptr: LI → CHHODI ✅

Yaad rakho: RAII object ko kabhi new se mat banao. Stack pe banao, ya unique_ptr mein rakho.

Trap 2: copy kiya toh ek cheez do baar delete

Analogy: ek locker, ek chaabi. Tumne duplicate chaabi bana ke dost ko de di. Jaate waqt tum locker tod ke phenk dete ho. Phir dost bhi wahi locker todne jaata hai, jo hai hi nahi. Crash.

Buffer a(10);    // a ke paas memory ka pointer (chaabi)
Buffer b = a;    // b ko SAME pointer mil gaya (duplicate chaabi)
}                // b ka destructor: delete ✅
                 // a ka destructor: wahi memory phir delete ❌
free(): double free detected   → crash

Default copy sirf pointer copy karta hai, memory nahi (shallow copy). Do objects, ek memory, do baar delete.

Fix (sabse simple): duplicate chaabi banana hi band.

Buffer(const Buffer&) = delete;              // copy band
Buffer& operator=(const Buffer&) = delete;   // copy assignment band
Buffer b = a;  →  error: use of deleted function 'Buffer::Buffer(const Buffer&)'

Galti code chalne se pehle hi pakdi gayi. unique_ptr bhi yahi karta hai, isliye wo copy nahi hota (sirf move: chaabi kisi aur ko de di, apne paas nahi rahi). Aur bhi aasaan: class mein raw pointer rakho hi mat. int* data ki jagah vector<int> data, vector khud sambhaal lega. (Deep copy wala tareeka: #58.)

Trap 3 (ek line): destructor mein exception mat phenko

Destructor ka kaam chupchaap safai karna hai. Safai karte karte hi ek aur problem khadi kar di, toh C++ program seedha band kar deta hai (terminate).

Trap 4 (ek line): constructor beech mein fail hua toh destructor nahi chalta

Constructor chal raha hai:
   1. file kholi        ✅
   2. memory maangi     ❌ fail (exception)
→ object poora bana hi nahi → destructor nahi chalega
→ file khuli reh gayi (leak)

Fix: har resource ko uska apna RAII member do (jaise unique_ptr). Jo member ban chuka tha, wo khud saaf ho jaata hai:

Bad  (raw pointer member):  file khuli → catch               ❌ file kabhi band nahi
Good (unique_ptr member):   file khuli → file band → catch   ✅

8. Interview mein

Interview mein

"RAII stands for Resource Acquisition Is Initialization. The idea is to tie a resource's lifetime to an object's lifetime: the constructor acquires the resource and the destructor releases it. C++ guarantees that a stack object's destructor runs when it goes out of scope, whether the function returns normally, returns early or exits through an exception. During an exception, stack unwinding destroys all local objects in reverse order. So resources can never leak. The standard library is built on this: vector and string for memory, unique_ptr and shared_ptr for heap objects, fstream for files, and lock_guard for mutexes, which prevents a lock from staying held after an exception. The common pitfalls are creating the RAII object itself with raw new, and copying a class that owns a raw resource, which causes a double free; we prevent that by deleting the copy operations, implementing a deep copy, or better, following the Rule of Zero with unique_ptr or vector members. Compared to a garbage collector, RAII is deterministic and works for any resource, not just memory."

Follow-upShort answer
How does it work with exceptions?Stack unwinding: local objects' destructors run in reverse order of construction.
When does RAII fail?When the RAII object is created with raw new and never deleted, or when it is shallow-copied.
Why can't unique_ptr be copied?There would be two owners and a double delete, so it is move-only.
Can a destructor throw?It should not. Destructors are noexcept by default, and throwing during unwinding calls std::terminate.
Give an RAII example.lock_guard: the constructor locks the mutex and the destructor unlocks it.
Why is RAII better than GC?Cleanup is deterministic and it handles any resource, not just memory.

Self-check

1. RAII ek line mein, aur ek example.

Resource ki zindagi object ki zindagi se baandh do: constructor lo, destructor chhodo. Example: lock_guard constructor mein lock leta hai, } pe destructor unlock karta hai.

2. Exception aane pe bhi memory kaise free hoti hai?

Stack unwinding: exception bahar nikalte waqt scope ke saare local objects ke destructors chalte hain (reverse order), catch tak pahunchne se pehle.

3. Buffer* p = new Buffer; mein RAII kyun fail hua?

new wala object kisi } se bandha nahi, toh destructor tab tak nahi chalta jab tak delete na karo. Fix: make_unique<Buffer>().

4. RAII class copy karne pe crash kyun, aur fix?

Default copy sirf pointer copy karta hai, toh do objects ek memory, do baar delete (double free). Fix: copy = delete, ya raw pointer ki jagah vector/unique_ptr member.

5. Trap 3 aur 4 ek ek line mein.

3: destructor mein exception mat phenko, warna terminate. 4: constructor fail hua toh destructor nahi chalta, isliye har resource ko apna RAII member do.
