1. RAII kya hai? (ek line mein)

Core idea

Resource ki lifetime ko ek object ki lifetime se baandh do. Object bana → resource mila (constructor). Object scope se bahar gaya → resource chhoda (destructor).

Naam confusing hai, idea simple hai. Naam ka matlab: "resource lena = object ka initialize hona". Yaad rakhne ke liye ise "Scope-Bound Resource Management" samjho.

Resource kya-kya ho sakta hai? Sirf memory nahi:

ResourceLena (acquire)Chhodna (release)
Heap memorynew / mallocdelete / free
Fileopen / fopenclose / fclose
Mutex locklock()unlock()
Network / DB connectionconnectdisconnect

Har resource ka ek "lo" aur ek "wapas karo" hota hai. RAII ka kaam: "wapas karo" kabhi bhoolne mat do.

2. RAII ke 2 core principles

Principle 1: Resource Acquisition (constructor mein lo)

Object banta hai → constructor zaroori resource le leta hai. Example: FileHandler object bana → constructor ne file khol di.

Principle 2: Resource Release (destructor mein chhodo)

Object scope se bahar gaya (function khatam, block } khatam) ya delete hua → destructor apne aap chalta hai aur resource chhod deta hai.

Ye kaam kyun karta hai? C++ ki ek guarantee pe: stack object ka destructor scope khatam hote hi chalega, guaranteed. Programmer ko yaad nahi rakhna padta, compiler khud call daalta hai.

3. RAII kyun zaroori hai? (3 reasons)

ReasonMatlab
Bhoolne ka risk khatamclose() / delete khud call nahi karna padta, toh leak nahi hota
Exception safetyObject banne ke baad aur destroy hone se pehle exception aaya, tab bhi destructor chalega aur cleanup hoga
Clean codeHar function mein cleanup ka jhanjhat nahi. Resource management "invisible / implicit" ho jaata hai

Bina RAII ka dard (C style)

void save() {
    FILE* f = fopen("log.txt", "w");
    if (error1) { fclose(f); return; }   // har exit pe yaad rakhna
    if (error2) { fclose(f); return; }   // ek bhi bhoola = leak
    riskyFunction();                     // exception aaya? fclose kabhi nahi chalega!
    fclose(f);
}

Jitne exit points, utni baar fclose. Aur exception ka case toh handle hi nahi ho sakta.

4. Code example: apna FileHandler

class FileHandler {
    FILE* file;
public:
    FileHandler(const char* name) {               // ACQUIRE
        file = fopen(name, "w");
        if (!file) throw runtime_error("open failed");
        cout << "Constructor: file opened\n";
    }
    ~FileHandler() {                              // RELEASE
        if (file) fclose(file);
        cout << "Destructor: file closed\n";
    }
    void write(const char* msg) { fputs(msg, file); }

    FileHandler(const FileHandler&) = delete;            // copy band (Trap 2 dekho)
    FileHandler& operator=(const FileHandler&) = delete;
};

void risky() {
    FileHandler fh("log.txt");
    fh.write("hello\n");
    throw runtime_error("something broke");       // exception!
}

int main() {
    {
        FileHandler fh("log.txt");
        fh.write("hello\n");
        cout << "Scope end aa raha hai...\n";
    }                                             // ← yahan destructor khud chala

    try { risky(); }
    catch (const exception& e) { cout << "Caught: " << e.what() << "\n"; }
}
Constructor: file opened
Scope end aa raha hai...
Destructor: file closed
Constructor: file opened
Destructor: file closed        ← exception ke BAWAJOOD file band hui
Caught: something broke

Dhyaan do: exception case mein Destructor catch se pehle print hua. Ye stack unwinding hai: exception risky() se bahar nikalte waqt uske saare local objects ke destructors chalte hain (Top30 Q29 mein ~R Base wala output yahi tha). Developer ne close kahin call nahi kiya.

Mutex lock

7. Traps (interviewer yahan pakadta hai)

Saare traps ek sawaal pe tike hain: destructor kab chalta hai, aur kitni baar? RAII tabhi sahi chalta hai jab har resource ka destructor exactly ek baar chale. Trap 2 mein wo do baar chalta hai, Trap 3 mein ek baar bhi nahi, aur Trap 4 mein destructor khud gadbad karta hai.

Trap 1: RAII sirf stack object pe automatic hai

FileHandler* fh = new FileHandler("a.txt");   // heap pe
// delete bhool gaye → destructor kabhi nahi chalega → file kabhi band nahi

Fix: heap object ko bhi RAII mein lapeto: auto fh = make_unique<FileHandler>("a.txt");. Rule: Modern C++ mein raw new/delete likhna hi nahi chahiye.

Trap 2: Copy hua toh resource do baar free hoga

Jab tum Buffer b = a; likhte ho aur khud ka copy constructor nahi likha, toh compiler ka default copy constructor har member ki value as-it-is copy karta hai. Member pointer hai toh sirf address copy hota hai, memory nahi. Isko shallow copy kehte hain (Top30 Q10).

class Buffer {
    int* data;
public:
    Buffer()  { data = new int[5]; cout << "Constructor: memory li at " << data << endl; }
    ~Buffer() { cout << "Destructor: delete " << data << endl; delete[] data; }
};

int main() {
    Buffer a;
    Buffer b = a;      // default copy → shallow copy
    cout << "main khatam" << endl;
}

main khatam
Destructor: delete 0x562c609c82b0     ← b ne free kiya
Destructor: delete 0x562c609c82b0     ← a ne SAME address dobara free kiya
free(): double free detected in tcache 2
Aborted

FileHandler ke saath bilkul yahi hota hai: do objects, ek FILE*, do baar fclose.

Fix 1: Copy band kar do

FileHandler(const FileHandler&) = delete;
FileHandler& operator=(const FileHandler&) = delete;

= delete ka matlab: "compiler, ye function mat banana." Ab koi copy karega toh compile error aayega. Galti runtime crash ki jagah compile time pe pakdi gayi. Ye isliye kiya kyunki ek file ka ek hi malik hona chahiye.

Fix 2: Move allow karo

Move = malik badal do. Naya object resource le leta hai, purana khaali ho jaata hai (nullptr). Ab bhi malik ek hi hai, toh destructor bhi ek hi baar free karega. Copy = photocopy (do kaagaz ban gaye). Move = chaabi kisi aur ko dena (chaabi ek hi). unique_ptr exactly yahi karta hai: copy band, move allowed (detail).

Trap 3: Constructor ke beech mein exception, destructor chalega hi nahi

Rule

Destructor sirf us object ka chalta hai jo poori tarah ban chuka ho, yaani jiska constructor pura khatam ho gaya. Lekin constructor fail ho jaye, toh bhi jo members already ban chuke hain, unke destructors chalte hain.

❌ Raw members✅ RAII members
class Two {
    int* a; int* b;
public:
    Two() {
        a = new int[5];
        cout << "a ki memory li\n";
        throw runtime_error("b fail");
        b = new int[5];
    }
    ~Two() { delete[] a; delete[] b; }
};

Trap 4: Destructor se exception mat phenko

Exception aaya → C++ function se bahar nikalta hai → raste mein har local object ka destructor chalata hai (stack unwinding) → phir catch tak pahunchta hai. Agar cleanup ke dauraan hi ek destructor ne doosra exception phenk diya, toh hawa mein do exceptions ek saath hain. C++ ek waqt mein sirf ek handle kar sakta hai, isliye std::terminate() call karta hai aur program turant band.

class Bad {
public:
    ~Bad() { cout << "~Bad: exception phenk raha hoon" << endl;
             throw runtime_error("from destructor"); }
};
int main() {
    try { Bad b; throw runtime_error("pehla exception"); }
    catch (const exception& e) { cout << "Caught: " << e.what() << "\n"; }
}
~Bad: exception phenk raha hoon
terminate called after throwing an instance of 'std::runtime_error'
  what():  from destructor
Aborted

"noexcept by default" ka matlab: noexcept = function ka promise ki "main exception nahi phenkunga." C++11 se har destructor apne aap noexcept hota hai. Isliye pehla exception na bhi ho, destructor se exception nikla toh bhi terminate(). Compiler ne khud warning di thi:

warning: 'throw' will always call 'terminate'
note: in C++11 destructors default to 'noexcept'

Fix: destructor ke andar koi kaam fail ho sakta hai, toh error ko andar hi handle karo (log ya ignore), bahar mat phenko:

~FileHandler() {
    if (file && fclose(file) != 0) {
        cerr << "close failed\n";   // bas log kiya, throw nahi
    }
}

Trap 5: Destruction order

Ek scope mein kai RAII objects → reverse order mein destroy (Set 2 Q2). Lock pehle lo, file baad mein kholo, toh file pehle band hogi, lock baad mein chhootega. Order predictable hai.

8. Constructor/destructor khud likhne padte hain ya C++ deta hai?

Is sawaal mein do alag sawaal chhupe hain: call kaun karta hai aur likhta kaun hai.

Call kaun karta hai? → Hamesha compiler

{
    FileHandler fh("log.txt");   // compiler yahan constructor call daalta hai
    fh.write("hello");
}                                // compiler yahan destructor call daalta hai

RAII ka asli jaadu yahi hai: call automatic hai, isliye bhool hi nahi sakte.

Likhta kaun hai? → Resource pe depend karta hai

Case A: Ready-made RAII class use kar rahe ho → kuch nahi likhna. vector, string, fstream, smart pointers ke constructor/destructor library walon ne likh diye hain. Real code mein 90% time yahi hota hai.

void f() {
    vector<int> v(1000);        // constructor ne heap memory li
    ofstream file("log.txt");   // constructor ne file kholi
}                               // dono ke destructors ne khud chhoda

Case B: Raw resource ko wrap kar rahe ho → tumhe likhna padega. FILE*, raw new, OS handles RAII nahi hain. FileHandler exactly yahi tha.

Case C: Destructor nahi likha toh? Compiler ek default destructor bana deta hai jo sirf har member ka destructor call karta hai. Use nahi pata ki FILE* ko fclose karna hai ya pointer ko delete.

❌ Leak✅ No leak (Rule of Zero)
class Bad {
    int* data;
public:
    Bad() { data = new int[100]; }
    // destructor nahi likha
};
 
class Good {
    vector<int> data;
public:
    Good() : data(100) {}
    // destructor ki zaroorat hi nahi
};

Default destructor data naam ka pointer variable (8 bytes ka address) hata dega, par jis memory pe wo point kar raha tha wo free nahi hogi. Pointer ek "address likha hua kaagaz" hai: kaagaz phenk diya, par ghar abhi bhi occupied hai. Good mein default destructor vector ka destructor call karta hai, aur wo memory free kar deta hai. Isi ko Rule of Zero kehte hain: members RAII rakho, khud ka destructor likhne ki zaroorat khatam.

9. Interview mein kaise bolo

30-second answer

"RAII ka matlab hai resource ki lifetime ko object ki lifetime se baandh dena. Constructor resource acquire karta hai, destructor release karta hai. C++ guarantee deta hai ki stack object ka destructor scope exit pe chalega, chahe normal return ho ya exception, toh resource kabhi leak nahi hota. Standard library mein unique_ptr, shared_ptr, vector, fstream aur lock_guard sab RAII hain. Isi wajah se C++ ko garbage collector ki zaroorat nahi padti, aur cleanup deterministic hota hai."

Self-check

1. RAII ek line mein, aur ek example.

Resource ki lifetime object ki lifetime se baandh do: constructor acquire, destructor release. Example: lock_guard constructor mein lock leta hai, scope khatam hote hi destructor unlock karta hai.

2. Exception aane pe bhi file kaise band hoti hai?

Stack unwinding: exception function se bahar nikalte waqt us scope ke saare local objects ke destructors chalte hain, catch tak pahunchne se pehle.

3. RAII class ka shallow copy kyun crash karta hai, aur fix?

Dono objects same pointer pakadte hain, dono ke destructors same resource free karte hain → double free. Fix: copy constructor aur copy assignment = delete, ya move allow karo.

4. Constructor beech mein throw kare toh kya leak hota hai?

Us object ka destructor nahi chalta (object pura bana hi nahi), toh raw pointer members se li gayi memory leak hoti hai. Already-bane members ke destructors chal jaate hain, isliye resources RAII members mein rakho.

5. Destructor se exception kyun nahi phenkna chahiye?

Destructors by default noexcept hain (C++11), aur stack unwinding ke dauraan doosra exception aaya toh do exceptions ek saath ho jaate hain. Dono cases mein std::terminate().
