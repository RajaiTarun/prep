1. Problem: raw pointer ke saath 3 galtiyan

Dog* d = new Dog("Tommy");
GaltiKya huaResult
Leakdelete bhool gayeMemory kabhi wapas nahi mili

Core idea

Smart pointer = pointer ke upar RAII wrapper. Ek class jo andar pointer rakhti hai aur destructor mein khud delete karti hai (RAII). delete likhna hi nahi padta. C++ mein 3 hain: unique_ptr, shared_ptr, weak_ptr.

2. unique_ptr: sirf ek maalik

Analogy: ek locker, sirf ek chaabi. Duplicate chaabi ban hi nahi sakti. Chaabi kisi aur ko de sakte ho, par phir tumhare paas nahi rahegi.

{
    unique_ptr<Dog> d1 = make_unique<Dog>("Tommy");
    cout << d1->name;                  // normal pointer jaisa use
}                                      // } aaya → Tommy apne aap delete
Tommy bana
Tommy gaya     ← delete nahi likha phir bhi

Copy nahi hota (duplicate chaabi nahi):

auto d2 = d1;        // ❌
error: use of deleted function 'unique_ptr(const unique_ptr&)'

RAII ka Trap 2 (copy se double free) yaad karo. unique_ptr ne copy band karke wahi fix pehle se kar rakha hai.

Move hota hai (chaabi kisi aur ko de di):

unique_ptr<Dog> d2 = move(d1);
move ke baad: d1 nullptr, d2 = Tommy

Kab: by default hamesha yahi. 90% cases mein ek hi maalik hota hai. Size raw pointer jitna (8 bytes), koi extra cost nahi.

3. shared_ptr: kai maalik, aakhri wala band kare

Analogy: hostel ka common room TV. Log aate jaate hain, TV tab band hota hai jab aakhri insaan room chhodta hai. Bahar ek counter ginta hai andar kitne log hain.

{
    shared_ptr<Dog> s1 = make_shared<Dog>("Bruno");   // count = 1
    {
        shared_ptr<Dog> s2 = s1;                      // copy chalta hai! count = 2
    }                                                 // s2 gaya, count = 1
}                                                     // s1 gaya, count = 0 → delete
Bruno bana
count = 1
s2 = s1 ke baad count = 2
s2 ka scope khatam, count = 1
Bruno gaya          ← count 0 hua tabhi delete
Rule

Copy kiya → count + 1. Ek shared_ptr khatam → count − 1. Count 0 → object delete.

Count kahan rehta hai? Ek alag chhoti jagah mein: control block. Isliye shared_ptr ka size 16 bytes (object ka pointer + control block ka pointer), unique_ptr ka 8.

Kab: jab sach mein kai jagah ek hi object chahiye aur pata na ho ki aakhir mein kaun use karega.

4. weak_ptr: sirf dekhta hai, maalik nahi

Pehle problem: shared_ptr ka cycle

Ravi aur Priya dost hain, aur dono ek doosre ka shared_ptr rakhte hain:

struct Person { shared_ptr<Person> friendPtr; };

auto ravi  = make_shared<Person>("Ravi");
auto priya = make_shared<Person>("Priya");
ravi->friendPtr  = priya;     // Priya ka count = 2
priya->friendPtr = ravi;      // Ravi ka count = 2
count Ravi = 2, Priya = 2
scope khatam (koi 'gaya' nahi = LEAK)

Bahar wale ravi, priya gaye toh dono ka count 2 → 1. Par 0 kabhi nahi: Ravi tab marega jab Priya chhodegi, Priya tab jab Ravi chhodega. Dono hamesha wait karte rahenge.

Fix: weak_ptr

weak_ptr object ko dekh sakta hai par count nahi badhata. Maalik nahi, sirf "jaan pehchaan wala".

struct Person { weak_ptr<Person> friendPtr; };   // shared ki jagah weak
Ravi bana
Priya bana
Priya gaya    ✅
Ravi gaya     ✅

Use kaise karein? Pehle lock(): check karta hai object zinda hai ya nahi.

if (auto p = w.lock())     // zinda → shared_ptr mil gaya
    cout << p->name;
else                       // mar chuka → nullptr
    cout << "object nahi raha";
lock() mila: Max
... (Max gaya) ...
expired? 1
lock() = nullptr

Kab: cycle todne ke liye, ya jab object ko sirf dekhna ho, zinda nahi rakhna.

reset vs release

reset() = object delete karo. release() = object chhod do par delete mat karo (raw pointer wapas milta hai). release() ke baad delete bhoole toh leak. Bahut kam use hota hai.

Array

arr[1] = 20;
arr[1] = 20

Real code mein array ke liye zyada tar vector hi use karte hain.

6.2 shared_ptr

shared_ptr<Dog> a = make_shared<Dog>("Bruno");
shared_ptr<Dog> b = a;               // copy: count + 1
a.use_count();                       // kitne maalik
a.get() == b.get();                  // dono same object pe
b.reset();                           // b ne chhoda: count − 1, b = nullptr
use_count = 2, a.get() == b.get() ? 1
b.reset() ke baad: a.use_count = 1, b = nullptr

Function ko dena: by value vs by reference

void byValue(shared_ptr<Dog> p);          // copy bani: count + 1 (andar maalik)
void byRef(const shared_ptr<Dog>& p);     // copy nahi: count same
byValue ke andar count = 3
byRef ke andar count = 2

Sirf dekhna hai toh const shared_ptr& (ya seedha Dog&): count badhana-ghatana bhi thoda kaam hai.

if (shared_ptr<Dog> t = w.lock()) {  // use karna ho toh lock()

7. Traps (simple version)

Trap 1: ek raw pointer se do shared_ptr mat banao

Dog* raw = new Dog();
shared_ptr<Dog> s1(raw);
shared_ptr<Dog> s2(raw);    // ❌
free(): double free detected

Dono ko lagta hai wo akele maalik hain: do alag counters (control blocks), dono 1 pe. Dono ne delete kiya, crash. Fix: s2 = s1 (copy, count ek hi). Usse bhi achha: raw new likho hi mat.

Trap 2: hamesha make_unique / make_shared

auto d = make_unique<Dog>("Tommy");   // ✅
unique_ptr<Dog> d(new Dog("Tommy"));  // chalta hai, par raw new dikh raha hai

make_ se raw pointer kabhi haath mein aata hi nahi, toh Trap 1 ho hi nahi sakta. make_shared object aur count ko ek hi allocation mein banata hai, thoda fast.

Trap 3: shared_ptr cycle = leak

Ravi/Priya wala case (section 4). Fix: ek side weak_ptr.

9. Interview mein

Interview mein

"Smart pointers are RAII wrappers around raw pointers: they delete the object in their destructor, so we avoid leaks, double deletes and dangling pointers. unique_ptr models exclusive ownership. It cannot be copied, only moved, and it has no overhead over a raw pointer, so it is the default choice. shared_ptr models shared ownership: it keeps a reference count in a control block, copying increments the count, destruction decrements it, and the object is deleted when the count reaches zero. Its weakness is cycles: if two objects hold shared_ptrs to each other, the counts never reach zero and they leak. weak_ptr solves this: it observes a shared_ptr-managed object without increasing the count, and we call lock() to get a shared_ptr if the object is still alive. We should create them with make_unique and make_shared, and never create two shared_ptrs from the same raw pointer."

Follow-upShort answer
Why can't unique_ptr be copied?There would be two owners and a double delete, so it is move-only.
When does shared_ptr delete the object?When the reference count reaches zero.
Where is the reference count stored?In a separately allocated control block.
Why do we need weak_ptr?To break shared_ptr cycles, because it does not increase the count.
How do you use a weak_ptr?Call lock(); it returns a shared_ptr, or null if the object is gone.
Why make_shared?No raw new in sight, and the object and control block share one allocation.
reset() vs release()?reset() deletes the object; release() gives up ownership without deleting and returns the raw pointer.
How do you pass a unique_ptr to a function?By reference or raw pointer to just use it; by value with std::move to transfer ownership.

Self-check

1. Smart pointer ek line mein.

Pointer ke upar RAII wrapper: destructor mein khud delete, toh leak, double delete, dangling se bachata hai.

2. auto d2 = d1; unique_ptr pe kya hoga, aur ownership kaise doge?

Compile error (copy band). auto d2 = move(d1); → d1 nullptr, d2 maalik.

3. shared_ptr ka count kab badhta, kab ghatta hai?

Copy pe +1, ek shared_ptr khatam ya reset() pe −1. 0 hua toh delete. By value function mein bheja toh andar +1.

4. Cycle kya hai aur fix?

Do objects ek doosre ka shared_ptr rakhein toh count 0 nahi hota, leak. Ek side weak_ptr, kyunki wo count nahi badhata.

5. reset() aur release() mein farak?

reset() delete karta hai. release() sirf ownership chhodta hai, raw pointer deta hai, delete tumhe karna hai.
