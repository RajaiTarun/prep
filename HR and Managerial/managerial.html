MerchFlow (about 80 seconds)

MerchFlow is a merch portal for college clubs. I started by talking to club admins and students. Every club used its own Google Form or website and size chart, so students ordered wrong sizes and missed delivery slots lost in email. I built one portal: students save one standard size and get delivery-slot alerts, and admins manage orders.

It is five Node.js and Express microservices: API gateway, user, catalog, order and notification. I chose PostgreSQL for orders because they need ACID transactions, MongoDB for the catalog because items have varying attributes, Redis for caching and locks, and RabbitMQ so a slow notification service can't delay checkout.

The hardest part was checkout during flash sales. I used a per-item Redis lock, idempotency keys so retried requests don't create duplicate orders, and a Saga that restores stock if payment fails. I cached the catalog feed in Redis, about 40% faster, and invalidated it on every stock write after users saw stale counts.

I tested every feature against a 58-item checklist, and I fixed a race condition in the rate limiter and verified it with 50 concurrent requests.

Expect: microservices vs monolith; why PostgreSQL vs MongoDB; what happens if the lock holder crashes; how idempotency keys work; Saga: choreography or orchestration, and what if a compensation fails; how you measured the 40%; which rate-limiting algorithm and how the race happened; how JWT and role-based access work; how you would scale or deploy it. Practise these on Thu 26 in the 7-day plan (MerchFlow quizzes). Docker is not on your resume: if asked, say so honestly.

POSIX shell (about 60 seconds)

I built an interactive Unix shell in C++ from scratch on POSIX system calls: fork, execvp, pipe, dup2, waitpid and sigaction. It supports N-stage pipelines, I/O redirection and background jobs. I split it into four modules: ProcessExecutor, JobController for background jobs and zombie reaping, BuiltinEngine for cd, ls, pinfo and search, and HistoryManager.

I was careful with signals: the Ctrl+C handler only sets a flag that the main loop checks, and the shell ignores Ctrl+Z while the child does not, so only the running command is suspended. History keeps the last 20 commands in a bounded deque with O(1) eviction, saved to a file across sessions.

Expect: what happens when you run ls | grep a > out.txt &; why fork before exec; dup vs dup2; zombie vs orphan; why the handler only sets a flag; pipe code in C (Anubhav was asked to write it).

Kafka-style event log (about 70 seconds)

With one teammate I'm building a Kafka-style distributed event log in C++17 and gRPC for our Distributed Systems course. Topics are split into partitions stored as append-only logs. Each partition is replicated across three brokers with leader–follower replication and a commit watermark, so consumers read only records held by every in-sync replica.

A 3-node Raft cluster elects partition leaders, and leader epochs fence stale leaders, so a leader that recovers after a pause can't cause split brain. Producers are idempotent, using producer IDs and sequence numbers. We verified it with 28 GoogleTest cases and 6 fault-injection tests: leader and consumer crashes and a full-cluster restart, with no acknowledged records lost.

My part was [exactly what you built, vs your teammate]

Expect: partitions, offsets, replication and the watermark; Raft election and what a partition does to it; leader epochs; idempotent producers; where it sits in CAP (Kashif was asked CAP and hashing); gRPC benefits and limits (Vanshika); your role vs your teammate's.

3. Hypothetical questions: the think-aloud method

Your file says it best

“The main thing is to explain how you would handle the situation logically and calmly.” Use four steps, out loud: 1 Clarify (goal, deadline, who is affected) → 2 Plan (steps, order, risks) → 3 Communicate (who needs to know, and when) → 4 Deliver + review (check, learn). Then, if you have one, add a real short example.

5. Questions to ask the manager

Seniors: “Managers really like it if you have a technical discussion with them or ask something about MATLAB or MathWorks” (Aashrey). A GfG report says the interviewer asked first whether the candidate had questions, so prepare them now. Best four, in order:

  • How does MathWorks test MATLAB and Simulink across releases and platforms?
  • How do EDG engineers usually choose their first team, and what does a first project look like?
  • How are agentic AI tools used in day-to-day development on your team?
  • What do you look for in an EDG engineer after the first year?

More options are on the Connect page.

6. Do and Don't for this round

DoDon't
  • Start with the problem and the users, not the tech stack.
  • Draw the architecture on paper or screen while you speak.
  • Say “I decided…” for your decisions and “my teammate did…” for theirs.
  • Think aloud and ask clarifying questions (Piyush).
  • Ask for feedback at the end (GfG reports).
  • Claim skills you can't explain two levels deeper (Nikhil).
  • Turn it into a debate with the interviewer.
  • Blame teammates or professors in any story.
  • Talk about Docker, Java or Python as strengths: they aren't on your resume.
  • Memorise word for word.
