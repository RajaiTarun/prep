Phase 1: Project ko scratch se samajhna

POSIX shell (C++). Hinglish notes. Phase 1 ka kaam: bada picture, fork/exec ki basic samajh, aur 1-2 min ka pitch.

Is phase ke baad tum ye kar paoge: apne project ko bina code dekhe 1-2 minute mein samjha sako, aur ye bata sako ki jab user ek command type karta hai to shell andar se kya karta hai.
Plan: kya hai → kyun → kya-kya implement hai → components → Enter dabane par flow → built-in vs external → fork + exec → foreground vs background → doubts → pitch.

1. Shell kya hai, aur hum kyun banate hain?

Kernel (OS) sirf system calls samajhta hai: "process banao", "file kholo". Insaan seedha system calls nahi bol sakta. Shell ek translator hai: jo hum type karte hain use system calls mein badal deta hai. Shell khud ek normal program hai jo ek infinite loop mein chalta hai:

loop:
   prompt dikhao
   ek line padho
   samjho kya chalana hai
   chalao
   (wapas upar)

Ye main.cpp ka while (1) hai. Isse REPL kehte hain: Read, Evaluate, Print, Loop.

POSIX kya hai? POSIX ek standard hai (Unix-type systems kaise behave karein). Ye kisi shell ka naam nahi. Isliye project ko bolo "POSIX-style shell", "POSIX shell" ya "fully POSIX compliant" nahi (README mein ye overclaim hai, interview mein mat bolna).

Hum ye kyun banate hain? Ye Operating Systems course ka assignment tha. Shell banane se fork, exec, pipe, signals jaise cheezein sach mein samajh aati hain, kyunki shell inhi sab ka asli use hai.

6. External command ka safar: fork → exec

Shell ls ko apne andar chalata to ls ke saath shell bhi khatam ho jaata. Isliye shell nayi process banata hai (fork), us nayi process ko cat bana deta hai (exec), aur khud zinda rehta hai.

6a. fork(): photocopy machine

Maan lo tum ek kitaab line 5 tak padh chuke ho. fork() ek photocopy bana deta hai: ek duplicate padhne wala, jo bilkul usi line 5 par khada hai, usi kitaab aur usi yaadasht ke saath. Ab dono line 6 se aage apni-apni kitaab padhte hain.

  • Parent = original. Child = photocopy.
  • fork() ke baad dono ek saath chalte hain, aur dono wahi code fork() ki agli line se chalate hain.

Asli program ka output:

int x = 10;
printf("1) fork se PEHLE ...");

pid_t p = fork();          // <-- yahan 2 hisse ho jaate hain

if (p == 0)      { x = 99; printf("2) Main CHILD hoon ... p=%d x=%d", p, x); }
else if (p > 0)  {         printf("3) Main PARENT hoon ... p=%d x=%d", p, x); }
else             { perror("fork"); }
1) fork se PEHLE: main hi hoon, mera pid=16590
2) Main CHILD hoon.  fork ne mujhe 0 diya.     mera pid=16597, mere parent ka pid=16590, x=99
3) Main PARENT hoon. fork ne mujhe 16597 diya. mera pid=16590, x=10

Teen cheezein is output se:

  1. Line 1 sirf ek baar, 2 aur 3 dono kyun? Line 1 fork() se pehle thi, tab sirf ek process tha. Baad mein do process hain, dono if/else tak pahunchte hain: ek if (p == 0) wala hissa chalata hai, dusra else if (p > 0) wala.
  2. Kaun parent, kaun child? fork() ki return value se:
    Kaunfork() ne kya return kiya
    Child0
    Parentchild ka pid (positive number)
    Error-1 (koi child nahi bana)
  3. x alag kyun (99 vs 10)? Child ko apni khud ki copy milti hai sab variables ki. Child ne x = 99 kiya to sirf uski copy badli.

Mere project mein fork() teen jagah hai (ProcessExecutor.cpp), teeno mein wahi pattern:

FunctionKabKitne child
execute_foregroundcat file.txt1
execute_backgroundsleep 5 &1
execute_pipelinels | grep txthar stage ke liye ek (loop mein)
pid_t pid = fork();
if (pid == 0) {
    // CHILD: command chalane ki taiyari
} else if (pid > 0) {
    // PARENT (shell): child ko sambhalta hai
} else {
    perror("fork failed");   // fork fail hua, koi child nahi bana
}
Shell mein child tab banta hai jab user external command deta hai. Builtins mein fork() hota hi nahi.

6b. exec: dimaag badal do, body wahi rahe

fork() ke baad child shell ki hi copy hai. Par humein cat chalana hai. Analogy: ek aadmi (process) ka dimaag (program) nikaal ke cat ka dimaag laga do. Naam aur ID (pid) wahi rehti hai, par ab wo cat ki tarah kaam karta hai.

CHILD: exec se PEHLE mera pid=17952, main abhi shell-demo program hoon
CHILD: exec ke BAAD  mera pid=17952, ab main /bin/sh program hoon    ← pid SAME, program badal gaya
PARENT: child (pid=17952) khatam, mera kuch nahi badla               ← parent pe koi asar nahi

execvp("cat", args) ki 3 baatein:

BaatMatlab
pid nahi badaltaNaya process nahi banta, sirf program badalta hai
Success pe return nahi kartaPurana code khatam, uske neeche ki lines kabhi nahi chalti
Fail pe -1 return karta haiTab hi neeche ki line chalti hai

Mere code mein execvp ki return value ko -1 se compare nahi kiya gaya. Bas ye maana gaya ki agar agli line tak pahunche, to exec fail hua (kyunki success pe wo line exist hi nahi karti). Isiliye execvp ke turant baad perror(...) aur exit(...) hai. Wo lines sirf tab chalti hain jab exec fail ho (galat command). Demo:

nosuchcommand: No such file or directory      ← perror ne chalaya
CHILD: exec fail hua, ye line tabhi chali      ← exec ke neeche wali line

exit zaroori kyun? Agar fail hone par child exit na kare, to wo bhi shell ka loop chalane lagega, yaani 2 shells ban jayenge.

Naam ka matlab: v = arguments vector/array mein, p = command PATH mein dhoondta hai (isiliye "cat" likhna kaafi hai).

Fork aur exec alag kyun? fork sirf naya process banata hai, exec sirf program badalta hai. Alag hone se beech mein child apni setup kar sakta hai (pipe, redirection, signals, Phase 4 mein) aur parent shell zinda rehta hai.

    signal(SIGTSTP, SIG_DFL);

Ye execute_foreground ka child wala hissa hai.

6d. Foreground vs background: bada difference

Dono mein fork + exec same hai. Fark sirf ye hai ki parent kya karta hai fork ke baad.

Foreground: parent child ke khatam hone tak ruka rehta hai. Background: parent ruke bina prompt par aa jaata hai, aur child baad mein reap hota hai (iski detail Phase 3 mein).

Yahan "wait" aur "reap" sirf naam se bole hain. Zombie aur wait/waitpid ki detail parked hai (Phase 3-4), par un sections ko Phase 3 aur Phase 4 pages mein pehle se rakh diya hai.

7. Doubts jo aaye the (aur unke jawab)

Q1. "fork ke baad child ka pid 0 hona chahiye na?"

Do alag cheezein mix ho gayi thi:

CheezKya haiChild ke liye value
pid (getpid())Process ka asli ID number, jaise employee IDKoi asli number, jaise 17952
fork() ki return value (p)Ek sandesh jo fork() har process ko deta hai0

Child ka asli pid 0 nahi hota (pid 0 kisi normal process ka hota hi nahi). fork() child ko 0 sirf isliye deta hai taaki wo code mein pehchaan sake "main child hoon" (if (p == 0)).

Analogy: naya employee join hua. Uska employee ID 17952 hai (pid). HR ne use chit di: "0 = tum naye ho" (return value). Purane employee (parent) ko chit mili: "tumhara naya bachcha 17952 hai".

Parent ko jo value milti hai wo specifically child ka pid hai, taaki parent ko pata ho kis child ka wait karna hai (Phase 4 mein kaam aayega).

Q2. "fork ke baad naya child process banta hai na?"

Haan, bilkul sahi. Aur exec?

CallNaya process banta hai?pid
fork()HaanNaya pid

Q3. "perror wali line tab chalti hai jab child exit nahi hua?"

Condition "child exit hua ya nahi" nahi hai. Condition ye hai: execvp fail hua ya nahi.

  • exec safal → purana code mit gaya, perror wali line ab exist hi nahi karti.
  • exec fail → execvp -1 return karta hai, purana code zinda hai, to agli line perror(...) chalti hai, phir exit.
execvp ke neeche ki line tabhi chalti hai jab exec fail ho. exit wahan perror ke baad aata hai, uski wajah se error nahi chalta.

Q4. "Builtin ke saath & ignore ho jaata hai, aur wo foreground jaisa chalta hai?"

Haan. & builtin se pehle hat jaata hai, to builtin ko dikhta hi nahi. Maine chalake dekha: pwd & seedha path print karta hai (koi job id nahi), aur cd / & ne directory sach mein badal di.

"Foreground jaisa" ka nuance: ye execute_foreground function nahi hai. Builtin mein koi child banta hi nahi (fork nahi). Wo shell ke apne process ke andar chalta hai, aur jab tak khatam na ho shell ruka rehta hai.

Builtin (pwd &)Foreground external (sleep 5)
Child banta hai?NahiHaan (fork)
Shell kya karta haiKhud kaam karta hai, tab tak rukawaitpid mein ruka

Aisa kyun: background ka matlab hai alag process mein chalana. Builtin ko alag process mein chalate to cd jaisa builtin bekaar ho jaata (manager/intern wali baat). Isliye & chupchaap ignore hota hai.

Surprising side-effect: ls, search, pinfo mere shell mein builtin hain, to ls & bhi background mein nahi jaata, shell block karke chalta hai (asli bash mein ls external hai, wahan ls & sach mein background jaata).

Interview mein: "Mere shell mein builtins & ke saath bhi foreground behave karte hain, kyunki wo shell ke process mein chalte hain. Improve karne ke liye unhe fork karna padta."

Q5. "wait/waitpid samajh nahi aaya, aur child kahan banta hai?"

Meri galti thi: wait/waitpid, fork se pehle sikha diya tha. Ab order sahi hai: pehle fork (6a), phir exec (6b), phir poora trace (6c). Wait/waitpid Phase 4 mein execute_foreground ke code ke saath aayega. Kahan banta hai: ProcessExecutor.cpp ke teen functions mein (6a ki table).

11. English speech (1 to 2 minute)

Roughly 250 words, about 1.5 to 2 minutes at a normal pace. Learn the flow, not the exact words. Pause at each paragraph.

Full version (~1.5 to 2 min)

"I built a POSIX-style shell in C++, using system calls. It started as an assignment in my Operating Systems course in the first semester, but I found it interesting, so in June 2026 I rebuilt it from scratch to understand every part properly.

The shell is a REPL: it prints a prompt, reads a line, executes it, and goes back to the prompt. It first splits the line on semicolons into separate commands, and then splits each command on spaces into tokens.

After that it makes a few decisions. Does the command contain a pipe or a redirection? Does it end with an ampersand, which means it should run in the background? And is it a built-in? Built-ins like cd run inside the shell process itself, because cd changes the shell's own current directory. If I ran it in a child process, the child would change its directory and exit, and the shell would stay where it was.

For external commands, like cat or sleep, the shell calls fork to create a child process, and the child calls execvp to replace itself with the actual program. The parent shell stays alive. For a foreground command, the parent waits for the child to finish. For a background command, it does not wait: it returns to the prompt immediately, and a job controller cleans up the finished child later.

Besides this, the shell supports pipelines, input and output redirection, Ctrl+C and Ctrl+Z handling, and a persistent command history."
