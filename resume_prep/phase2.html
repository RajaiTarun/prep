2.1 Bada architecture: manager aur uski team

Mere shell ka code ek manager aur 4 helpers ki team jaisa hai. Manager (main.cpp) khud kuch execute nahi karta, wo sirf loop chalata hai, input padhta hai, parse karta hai, aur sahi helper ko kaam deta hai.

Har module ka sirf ek kaam

ModuleEk kaammain isse kaise bulata hai
main.cppLoop, prompt, input, ; split, tokenize, pipeline parse(ye khud manager hai)
BuiltinEngineBuiltin commands shell ke andar chalanabuiltin.execute(tokens). true mila to builtin tha, false to nahi
ProcessExecutorChild banake external command chalanaexecute_foreground, execute_background, execute_pipeline

Dependencies (kaun kisko use karta hai), code se verified

  1. Sab 4 objects main() mein bante hain (lines 241-244): JobController, ProcessExecutor, HistoryManager, BuiltinEngine.
  2. BuiltinEngine → HistoryManager: BuiltinEngine ko HistoryManager ka reference milta hai (BuiltinEngine builtin(homeDir, historyManager)), kyunki history command ko pichhle commands dikhane hain.
  3. ProcessExecutor → JobController: execute_background ko JobController parameter mein milta hai, taaki wo naye job ko register (addJob) kar sake. Foreground aur pipeline ko JobController ki zarurat nahi.
  4. BuiltinEngine → Commands/: ls, search, pinfo ke liye BuiltinEngine har baar ek naya LSCommand / SearchCommand / PinfoCommand object banata hai aur uska execute chalata hai.

Do cheezein jo seedha bolni chahiye (honest)

  • Parser alag class nahi hai. splitCommands, tokenize, parsePipeline main.cpp ke free functions hain. Struct CommandStage ProcessExecutor.h mein define hai aur parser use bhi karta hai.
  • README ka diagram mostly sahi hai, par usme exit ko BuiltinEngine ke andar dikhaya hai. Asli code mein exit main.cpp (line 302) mein pehchana jaata hai, BuiltinEngine tak pahunchta hi nahi.

Ek line mein

Manager (main.cpp) loop chalata hai aur parse karta hai; kaam 4 helpers ko deta hai: builtins, process execution, job tracking aur history. Do dependencies hain: BuiltinEngine → HistoryManager aur ProcessExecutor → JobController.

Check karo

  1. BuiltinEngine ko HistoryManager kyun chahiye?
  2. execute_background ko JobController kyun milta hai, par execute_foreground ko nahi?

Check ke jawab (tumhare jawab + sudhaar)

1. BuiltinEngine ko HistoryManager kyun? Tumhara idea sahi: history command ko pichhle commands dikhane hain. Ek detail galat thi: history command file nahi padhta. Wo HistoryManager ke memory wale deque (historyLedger) se padhta hai. File sirf do jagah use hoti hai: shell start pe load (constructor), aur band hone pe save (saveToFile).

Interview-level baat: BuiltinEngine ke paas HistoryManager ka reference hai, copy nahi. Isse jab main naya command addCommand karta hai, BuiltinEngine ko wahi updated history dikhti hai. Copy hoti to purani history hi dikhti.

2. execute_background ko JobController kyun? Tumhara jawab bilkul sahi. Thoda aur: background job ko register karna padta hai (pid, command text, job id) taaki JobController baad mein use reap kare aur [ 1 ] done ... print kare. Foreground mein parent turant waitpid karta hai, to track karne ko kuch bachta hi nahi.

2.2 Shell start hone par kya hota hai (boot)

Jab tum ./a.out chalate ho, main() loop se pehle ye kaam hote hain (main.cpp lines 230-245). Ye sirf ek baar hota hai.

Ek important baat

History file se do baar judti hai: start pe load, exit pe save (Ctrl+D ya exit command). Beech mein sab kuch memory ke deque mein hota hai. Isiliye agar shell crash ho jaaye ya kill ho jaaye, us session ki history save nahi hogi.

Ek line mein

Shell start hone par signals set hote hain, prompt ki details nikalti hain, 4 objects bante hain (history purani file se load hoti hai), banner dikhta hai, aur phir loop shuru hota hai.

Check karo

  1. Startup mein signals kyun set kiye gaye? (apne words mein, ek-do line)
  2. History file kab padhi jaati hai aur kab likhi jaati hai? Aur history command chalne par file padhi jaati hai?
